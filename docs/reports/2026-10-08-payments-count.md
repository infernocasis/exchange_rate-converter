# Количество оплат в разбивке по валютам

- **Дата:** 2026-10-08
- **Запрос:** тестовая фича для проверки правил: показать, из скольких оплат сложилась выручка — всего и по каждой валюте.

## Что сделано

Домен считает количество оплат тем же единственным проходом, что и суммы. Контракт `/api/revenue` расширен полями `paymentsCount` (в корне и в каждом элементе `breakdown`). UI выводит «14 оплат» в карточке итога и «9 оплат · 58,5 % от итога» в строке валюты, с русскими формами множественного числа через `Intl.PluralRules`.

## Финансовая проверка

Ручной прогон чистых функций (esbuild-бандл в scratchpad, курсы `USD=1, EUR=0.8, RUB=100`):

| Вход | Ожидалось | Получено |
|---|---|---|
| paid `0.1 USD`, paid `0.2 USD`, `"300 USD"` | 300.30 USD, 3 оплаты (без ошибки float) | `300.3`, `3` ✅ |
| refund с мусорными `amount`/`currency` | пропущен без ошибки | пропущен ✅ |
| paid `100 EUR`, `"50.55 EUR"` → USD | 150.55 × 1.25 = 188.1875 → **188.19** | `188.19`, `2` ✅ |
| `"1000 RUB"` → USD | 10.00 | `10`, `1` ✅ |
| итог | 300.30 + 188.19 + 10.00 = 498.49, 6 оплат; сумма строк = итог | `498.49`, `6`, `true` ✅ |
| пустые источники | `total: 0, paymentsCount: 0, breakdown: []` | совпало ✅ |

Живые данные: USD 3020.00 (9) + EUR 1910.00 → 2139.39 USD (5) = **5159.39 USD, 14 оплат** ✅

## Решения и риски

- Счётчик считается в домене, а не на клиенте: клиент получает только итоговые данные, исходные транзакции наружу не отдаются.
- `paymentsCount` — обязательное поле контракта; при добавлении новых источников оплат его нужно инкрементировать через тот же `addPayment`.
