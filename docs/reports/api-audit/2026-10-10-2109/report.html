Резюме

Сейчас API отдаёт данные, по которым выручка считается корректно: критичных проблем нет, все эндпоинты отвечают за ~1 с.

Главное к исправлению: все 9 строк GET /finance2 содержат код валюты в нижнем регистре ("300 usd", "200 eur"), тогда как GET /finance1 отдаёт "USD" / "EUR". Наш клиент приводит регистр сам, поэтому цифры верные, но это нарушение ISO 4217 и контракта: любой потребитель со строгим сравнением (=== "USD") получит ошибку или посчитает usd и USD как две разные валюты.

Рекомендации по контракту (не ломают расчёт сейчас, но мешают сверке): у транзакций /finance1 нет id и даты оплаты; /finance2 отдаёт плоские строки без id, даты и статуса — формат отличается от /finance1; в /finance1 приходит блок address, который к финансовым данным не относится.

Проблемы в финансовом API

🟡 CUR-CASE — Код валюты не в верхнем регистре

Где: GET /finance2 · Важность: Предупреждение · Найдено: 9

ГдеЗначениеКомментарий
[0]"usd"ожидается "USD"
[1]"eur"ожидается "EUR"
[2]"usd"ожидается "USD"
[3]"usd"ожидается "USD"
[4]"eur"ожидается "EUR"
[5]"usd"ожидается "USD"
[6]"usd"ожидается "USD"
[7]"usd"ожидается "USD"
…ещё 1полный список в findings.json

Влияние: Клиент нормализует регистр сам, поэтому расчёт верный. Но ISO 4217 требует верхний регистр, и любой другой потребитель API со строгим сравнением (=== "USD") получит ошибку или разнесёт одну валюту на две.

Как исправить: Отдавать коды валют в верхнем регистре: USD, EUR.

🟡 CUR-INCONSISTENT — Одна валюта записана по-разному

Где: GET /finance1 + GET /finance2 · Важность: Предупреждение · Найдено: 2

ГдеЗначениеКомментарий
USD"USD" в finance1; "usd" в finance2
EUR"EUR" в finance1; "eur" в finance2

Влияние: Клиент приводит написание к одному виду, но потребитель без нормализации посчитает одну валюту как несколько.

Как исправить: Единый формат кода валюты во всех эндпоинтах.

🔵 F1-NO-DATE — У транзакций нет даты

Где: GET /finance1 · Важность: К сведению · Найдено: 1

ГдеЗначениеКомментарий
transactions[*]нет полей date / createdAt / paidAt / timestamp / time

Влияние: Клиент не может проверить, что все оплаты относятся к нужному дню.

Как исправить: Добавить дату оплаты в ISO 8601 (2026-10-10T12:00:00Z).

🔵 F1-NO-ID — У транзакций нет уникального идентификатора

Где: GET /finance1 · Важность: К сведению · Найдено: 1

ГдеЗначениеКомментарий
transactions[*]нет полей id / _id / transactionId / uuid

Влияние: Невозможно отличить дубль от двух одинаковых оплат и сверить данные с учётной системой.

Как исправить: Добавить id в каждую транзакцию.

🔵 F1-ROOT-EXTRA — В ответе есть поля, не относящиеся к транзакциям

Где: GET /finance1 · Важность: К сведению · Найдено: 1

ГдеЗначениеКомментарий
bodyaddress

Влияние: Клиент их игнорирует. Если это персональные данные — лишняя утечка наружу.

Как исправить: Убрать из финансового эндпоинта поля, которые не нужны для расчёта, или вынести в отдельный эндпоинт.

🔵 F2-STRUCTURE — Платежи — плоские строки без структуры

Где: GET /finance2 · Важность: К сведению · Найдено: 1

ГдеЗначениеКомментарий
[*]9 элементов вида "300 usd"

Влияние: Нет id, даты и статуса: нельзя сверить, отфильтровать неоплаченные или найти дубли. Форматы двух источников разные.

Как исправить: Отдавать объекты в том же формате, что и /finance1: { id, type, amount, currency, date }.

Ожидаемый контракт

GET /finance1:

{ "transactions": [ { "type": "paid", "amount": 100.5, "currency": "USD" } ] }
  • type — строка в нижнем регистре: paid | pending | rejected; в выручку идёт только paid.
  • amount — число ≥ 0, не более 2 знаков после точки.
  • currency — код ISO 4217, 3 латинские буквы в верхнем регистре.

GET /finance2:

["300 USD", "150.50 EUR"]
  • Каждая строка — "<сумма> <ВАЛЮТА>": сумма с точкой и ≤ 2 знаками, один пробел, код ISO 4217 в верхнем регистре.

curl -H "x-api-key: $FINANCE_API_KEY" https://cpa-server-vtel.onrender.com/api/finance1
curl -H "x-api-key: $FINANCE_API_KEY" https://cpa-server-vtel.onrender.com/api/finance2
