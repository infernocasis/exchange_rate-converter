# Exchange Rate Converter — правила проекта

Nuxt 4 приложение «Выручка за день»: собирает оплаты из двух финансовых источников,
суммирует по валютам и пересчитывает в целевую валюту по курсам CurrencyFreaks.

## Команды

| Команда | Зачем |
|---|---|
| `npm run dev` | dev-сервер на `http://127.0.0.1:3000` (именно IPv4, см. `nuxt.config.ts`) |
| `npm run typecheck` | проверка типов (`vue-tsc`) — **обязательна после любых правок** |
| `npm run build` | сборка; запускать, если менялись `server/`, `nuxt.config.ts` или зависимости |

Тестового фреймворка пока нет. Не добавлять его без согласования.

## Архитектура и слои

```
app/          клиент (Vue): pages, components, composables, utils
server/
  api/        тонкие обработчики h3: конфиг -> сервис -> ответ; ошибки через toApiError
  services/   оркестрация: параллельные запросы + вызов доменных функций
  domain/     ЧИСТЫЕ функции расчёта денег. Без I/O, без Nuxt auto-imports
  utils/      адаптеры к внешним API, конфиг, ошибки
shared/types/ контракт API — общий для сервера и клиента
```

Правила слоёв:

- Направление зависимостей: `api → services → domain`; `utils/*Api` → `domain`. Домен ничего не импортирует из `utils`, `api`, `app`.
- Контракт ответа меняется **только** в `shared/types/revenue.ts`, и тогда в той же задаче правятся сервер и клиент.
- Клиент никогда не ходит во внешние API напрямую — только через `/api/*`.

## Работа с сервером

- **Секреты только в приватном `runtimeConfig`** (без `public`). Читать через `useRevenueConfig(event)`, который валидирует значения и бросает `ConfigError`.
- Новая переменная окружения = три правки: `nuxt.config.ts` (с комментарием `// NUXT_...`), `.env.example`, `useRevenueConfig`.
- **Внешние запросы — только через `fetchUpstream`** (`server/utils/upstream.ts`): там таймаут, `retry: 0` и вычищение query-string из сообщений (в query бывает API-ключ).
- Каждый внешний провайдер — отдельный адаптер в `server/utils/<name>Api.ts`, наружу отдаёт формат, не зависящий от провайдера. Смена провайдера = правка одного файла.
- Ключ кеша (`defineCachedFunction`) не должен содержать секреты.
- Ответы с данными о выручке — `Cache-Control: no-store`.
- Ошибки:
  - внутри — типизированные классы (`UpstreamError`, `ConfigError`, `InvalidDataError`);
  - наружу — только через `toApiError`, с машиночитаемым `data.code` из `RevenueErrorCode`;
  - новый код ошибки = добавить в `RevenueErrorCode` **и** в `DESCRIPTIONS` в `app/utils/describeRevenueError.ts` (TypeScript не даст забыть);
  - неизвестная ошибка → `INTERNAL`, детали только в `console.error` на сервере.
- Источник на Render может «просыпаться» до минуты: не уменьшать `NUXT_FINANCE_TIMEOUT_MS` и не возвращать загрузку на SSR (`server: false` в `useDailyRevenue` — осознанное решение).
- Лимит бесплатного тарифа CurrencyFreaks мал: не убирать кеш курсов и не делать лишних запросов при отладке — использовать `curl http://127.0.0.1:3000/api/revenue` 1–2 раза, а не в цикле.

## Правила работы с финансами

Это главный раздел. Нарушение любого пункта — баг, даже если «цифры сошлись».

1. **Деньги считаются в целых центах.** Сложение — только `toCents` → целые числа → `fromCents`. Никогда не складывать `number` с копейками напрямую (`0.1 + 0.2 !== 0.3`).
2. **Порядок: сначала сумма по валюте, потом одна конвертация.** Не конвертировать каждый платёж отдельно — копится ошибка округления.
3. **Округление — один раз, на сконвертированных центах** (`Math.round(cents * rate)`). Итог = сумма уже округлённых строк, чтобы разбивка всегда складывалась в итог без «потерянного цента».
4. **Курс всегда через базу провайдера:** `getRate(from, to)` = `rates[to] / rates[from]`. Не хардкодить курсы, не брать курс «наоборот» без деления.
5. **Валюта — ISO 4217:** прогонять через `normalizeCurrency` (trim + upper + `/^[A-Z]{3}$/`). Нет курса для валюты → `InvalidDataError`, а не тихий пропуск.
6. **Суммы — строгая валидация:** конечное число, `>= 0`; строки — только через `parseAmount` (не `Number()`/`parseFloat`, они пропускают `""`, `1e3`, `0x10`, `Infinity`). Не больше 2 знаков после точки.
7. **Входные данные — `unknown`**, пока не провалидированы. Невалидная запись среди оплат — ошибка всего расчёта (`InvalidDataError`), а не «пропустим и посчитаем остальное»: неправильная выручка хуже, чем никакой.
8. Учитываются только транзакции с `type === 'paid'`; остальные типы пропускаются **без** валидации.
9. Расчётные функции в `server/domain/` — чистые и детерминированные: одинаковый вход → одинаковый выход, без `Date.now()`, сети и глобального состояния.
10. **Форматирование — только на клиенте** через `app/utils/format.ts` (`Intl.NumberFormat`, локаль `ru-RU`). Сервер отдаёт числа, а не строки вида `"1 234,56 $"`.
11. Любое изменение формулы расчёта сопровождается ручной проверкой на примере в отчёте: вход → ожидаемый выход → фактический.

## Стиль кода

- TypeScript strict, без `any`. Для внешних данных — `unknown` + проверки/`asserts`-функции.
- Без точек с запятой, одинарные кавычки, отступ 2 пробела, trailing comma в многострочных литералах, `catch`/`else` с новой строки (как в существующих файлах).
- Функции маленькие и именованные по действию: `parseX`, `validateX`, `normalizeX`, `toX`, `createXApi`, `useX`.
- Фабрики вместо классов для адаптеров (`createFinanceApi(config)`), тип — через `ReturnType<typeof ...>`.
- Именованные константы для «магических» значений: `RATES_CACHE_MAX_AGE_S`, `CURRENCY_RE`.
- Комментарии на русском, короткие, объясняют **почему**, а не что. JSDoc `/** */` для экспортируемых функций с неочевидным контрактом.
- Vue: `<script setup lang="ts">`, `defineProps<{...}>()`, вычисления в `computed`, компоненты раскладывать по папкам с префиксом (`revenue/RevenueX.vue` → `<RevenueX>`).
- Стили — только Tailwind-классы в шаблоне; суммы с `tabular-nums`.
- Доступность: у живых областей `aria-live`/`aria-busy`, у кнопок понятный текст.

## Проверки перед тем, как сказать «готово»

1. `npm run typecheck` — без ошибок.
2. Если менялся `server/` — `npm run build` и один запрос `curl -s http://127.0.0.1:3000/api/revenue` (проверить форму ответа).
3. Если менялся UI — открыть страницу через Playwright MCP, сделать snapshot, убедиться, что нет ошибок в консоли.
4. Проверить, что в дифф не попали `.env`, ключи, `console.log` для отладки.
5. Написать отчёт (см. ниже).

## Отчёты и память

- После каждой законченной задачи — отчёт в `docs/reports/YYYY-MM-DD-<slug>.md` по шаблону `docs/reports/_TEMPLATE.md`.
- Аудит ответов внешнего API для backend-команды — навык `finance-api-audit` (`.claude/skills/finance-api-audit/`), отчёты в `docs/reports/api-audit/<дата-время>/`.
- Устойчивые решения, которые не видно из кода (почему так, договорённости, внешние ограничения), — в память агента, а не в отчёт.
